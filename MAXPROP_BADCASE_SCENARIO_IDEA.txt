MaxProp가 성능이 나쁘게 나오기 쉬운 "적대적" 시나리오 설계안 (아이디어)
========================================================

목표
- MaxProp가 직접/간접적으로 고려하지 않는 요소들을 한꺼번에 넣어,
  MaxProp의 강점(다음-만남 확률 기반 cost + threshold 기반 스케줄/드롭)이 깨지기 쉬운 환경을 만든다.
- 특히, 동적 트래픽(메시지 생성률이 시간에 따라 급격히 변함), 에너지 고갈, 속도/접촉시간 변화,
  링크 용량의 상황 의존(거리/간섭)을 결합해 "비정상(non-stationary) + 혼잡(congestion) + 짧은 접촉(short contact)"을 만든다.

핵심 컨셉(왜 MaxProp에 불리한가)
1) cost가 (1 - P_next)만 반영 -> 링크 용량/접촉 지속시간/혼잡/abort 위험을 직접 반영 못함
2) threshold는 avgTransferredBytes에 의존 -> 트래픽 급변(버스트) 시 반응이 늦고, 접촉 패턴에 의해 왜곡 가능
3) 드롭/스케줄이 hop/cost 중심 -> TTL 임박/대형 메시지/abort 유발 메시지에 대한 보호/정리가 약함
4) P_next 학습/전이는 "최근 만남" + "전이 지식 교환" -> 에너지/가동시간 변화로 그래프가 급변하면 추정이 쉽게 깨짐


------------------------------------------------------------
1) 시나리오 개요: Non-stationary Burst + Energy Duty Cycling + Variable Capacity
------------------------------------------------------------

시간
- 총 12시간(43200s) 시뮬레이션
- 업데이트 간격은 기본(0.1s) 유지 가능

노드 그룹(예시)
G1) Pedestrians (느림, 안정적)
- 속도: 0.5~1.5 m/s
- 인터페이스: 저속/저전력(블루투스급)
- 버퍼: 작음(예: 2~5MB)
- 에너지: 중간, 스캔 비용은 낮지만 오래가진 않음

G2) Cars (중간 속도, 접촉 다수)
- 속도: 5~20 m/s
- 인터페이스: Wi-Fi급(거리/간섭에 따라 용량 변동)
- 버퍼: 중간(예: 10~30MB)
- 에너지: 낮게 설정(많이 움직이고 스캔/전송이 많아 빨리 닳게)

G3) Drones / Express (매우 빠름, 접촉 매우 짧음)
- 속도: 30~80 m/s
- 인터페이스: 고속이지만 접촉시간이 짧아 대형 메시지 전송에 불리
- 버퍼: 큼(예: 50MB) 또는 오히려 작게(대형 메시지로 빨리 포화)
- 에너지: 매우 낮게(짧은 시간만 켜졌다 꺼지게) + duty cycling(활성 시간 창)

G4) Ferries (정해진 루트, 예측 가능하지만 특정 시간대만 의미)
- MapRouteMovement로 고정 루트
- 특정 시간대에만 등장/활성(activeTimes) -> 그래프가 "시간대별로" 바뀜

포인트
- 속도/활성시간/에너지 소모를 다르게 해서, "누가 언제 나타나는지"가 자주 바뀌는 비정상 접촉 그래프를 만든다.
- 이때 MaxProp의 P_next 학습/전이 지식이 빠르게 낡고, cost가 현실과 어긋나기 쉬워진다.


------------------------------------------------------------
2) 링크 용량(전송속도)과 무선 환경: MaxProp가 cost에 못 넣는 요소를 크게 만들기
------------------------------------------------------------

2.1 거리 의존 용량(추천)
- DistanceCapacityInterface 사용:
  - 가까우면 고속, 멀면 저속(전송이 접촉시간/거리의 함수가 됨)
- 의도:
  - MaxProp cost는 P_next만 보는데, 실제로는 "가까운 순간에만 고속"이라
    짧은 접촉에서는 대형 메시지가 거의 못 보내고 aborted/부분전송이 늘어남.

2.2 간섭/경쟁 기반 용량 저하(추천)
- InterferenceLimitedInterface 사용:
  - 밀집 지역에서 동시에 전송하려는 노드가 많으면 effective transmitSpeed가 감소
- 의도:
  - 트래픽 버스트 시점에 링크 용량이 급락 -> MaxProp의 threshold/cost가 전혀 반영 못함

2.3 이종 인터페이스(저속/고속 혼합)
- 어떤 그룹은 블루투스(저속)만, 어떤 그룹은 Wi-Fi(고속)만, 어떤 그룹은 2개 모두
- 연결 속도는 양쪽 transmitSpeed의 min으로 결정되므로
  "고속 노드가 저속 노드와 만나면 전체가 저속"이 되는 병목이 생김


------------------------------------------------------------
3) 에너지 모델: 그래프를 시간에 따라 깨뜨리기(비정상성 강화)
------------------------------------------------------------

에너지 모델(ActiveRouter에 내장)
- initialEnergy: 낮게(또는 그룹별로 범위)
- scanEnergy / scanResponseEnergy: 크게(스캔이 잦으면 빨리 소모)
- transmitEnergy: 크게(대형 메시지/버스트에서 급격히 소모)
- energyWarmup: 0 (초기부터 소모)

의도
- 버스트 구간에서 에너지가 급격히 닳아 "허브"가 갑자기 죽거나,
  duty cycling(activeTimes)으로 라디오가 꺼졌다 켜졌다 하며,
  MaxProp의 전이 지식(allProbs)이 현실보다 오래 남아 오판을 유도.


------------------------------------------------------------
4) 트래픽(메시지 생성) 설계: "국면 전환"을 강하게 만들기
------------------------------------------------------------

MessageEventGenerator는 time 범위를 지원함(time = t0,t1).
여러 generator를 동시에 두고, prefix만 다르게 해서 구간별 트래픽을 만들면 된다.

4.1 Phase 1 (0~1h): 저부하, 작은 메시지
- interval: 20~40s, size: 10~50KB
- TTL: 길게(예: 180~300min)
- 의도: MaxProp가 안정적으로 학습/전이 지식을 축적하게 함(이때의 지식이 이후 국면에서 "낡은 지식"이 됨)

4.2 Phase 2 (1~2h): 급격한 버스트 + 대형 메시지
- interval: 0.5~2s, size: 0.5~5MB
- 소스/목적지를 "핫스팟"으로 편중(예: 특정 2~3개 목적지로 집중)
- 의도:
  - 혼잡/간섭으로 실제 전송 용량이 급락, 대형 메시지가 aborted를 유발
  - MaxProp는 TTL/size/abort 위험을 cost에 직접 반영하지 못해 비효율 행동 증가

4.3 Phase 3 (2~3h): TTL 짧은 긴급 메시지 섞기
- interval: 1~5s, size: 5~50KB, TTL: 매우 짧게(예: 5~15min)
- 의도:
  - MaxProp의 hop/cost 중심 스케줄/드롭이 긴급 메시지를 보호하지 못하면 delivery 급락/지연 악화

4.4 Phase 4 (3~12h): 주기적 on/off 버스트 + 목적지 스위칭
- 10~15분마다 버스트 on/off (generator를 여러 개로 쪼개 time 범위를 반복 설정하거나,
  메시지 burst generator 사용)
- 목적지 편중을 시간대별로 바꿈(핫스팟이 이동)
- 의도:
  - "stationary한 만남 확률" 가정이 더 깨짐
  - 전이 지식이 time-varying graph를 못 따라가면 오판 증가


------------------------------------------------------------
5) 속도/접촉 지속시간을 시간에 따라 바꾸기(권장: ExternalMovement)
------------------------------------------------------------

MaxProp는 속도/접촉 지속시간을 직접적으로 cost에 넣지 않는다.
따라서 "짧은 접촉"을 강하게 만들면 MaxProp가 대형 메시지/스케줄에서 불리해진다.

구현 아이디어(개념)
- ExternalMovement 또는 시간대별 그룹(activeTimes)로
  - 특정 시간대에 드론/차량이 고속으로 지나가며 짧은 접촉만 만들게 함
  - 다른 시간대에는 느리게 움직이며 접촉이 길게 유지되게 함

의도
- 같은 '만남 빈도'라도 접촉 시간이 짧으면 실질 전송량은 매우 작아지는데,
  MaxProp는 P_next 기반 cost로만 판단해 이 차이를 반영 못한다.


------------------------------------------------------------
6) 왜 이 시나리오에서 MaxProp가 특히 깨질 가능성이 큰가(예상 실패 모드)
------------------------------------------------------------

FM-1) "P_next는 맞는데 전송이 안 되는" 상황(접촉시간/용량 부족)
- 드론/차량이 자주 만나긴 하는데, 접촉이 너무 짧아 대형 메시지 전송이 실패(abort)
- MaxProp는 cost를 낮게 보고 우선 전송하려 하지만 실제로는 낭비가 됨

FM-2) threshold 반응 지연 + 버스트로 인한 큐/드롭 왜곡
- avgTransferredBytes는 연결이 내려갈 때 업데이트되는 샘플 기반 -> 버스트 급변에 늦게 반응
- 버퍼 priority/non-priority 분할이 실제 혼잡 국면에 맞지 않아, 잘못된 메시지가 살아남고 좋은 메시지가 드롭됨

FM-3) 전이 지식(allProbs)이 에너지/활성시간 변화로 "틀린 지도"가 됨
- 특정 허브가 에너지 고갈로 죽었는데도, 전이 지식은 최신으로 남아 cost가 계속 그 허브 경유를 선호

FM-4) TTL 긴급 메시지의 보호 실패
- hop/cost 중심 정렬은 TTL 임박 메시지를 별도로 보호하지 않으므로,
  버스트/혼잡 구간에서 짧은 TTL 메시지가 버려지거나 늦게 전송됨


------------------------------------------------------------
7) (선택) 설정 파일로 옮길 때 사용할 수 있는 키워드 스케치
------------------------------------------------------------

인터페이스
- *.type = SimpleBroadcastInterface | DistanceCapacityInterface | InterferenceLimitedInterface
- *.transmitSpeed = 250k | 10M ...
- DistanceCapacityInterface.transmitSpeeds = ... (거리 구간별)

에너지(ActiveRouter의 EnergyModel)
- Group.initialEnergy = ...
- Group.scanEnergy = ...
- Group.scanResponseEnergy = ...
- Group.transmitEnergy = ...
- Group.energyWarmup = 0

트래픽(여러 generator로 구간 분할)
- Events.nrof = N
- EventsK.class = MessageEventGenerator
- EventsK.prefix = phase1a, phase2burst ...
- EventsK.interval = ...
- EventsK.size = ...
- EventsK.hosts = ...
- EventsK.tohosts = ...
- EventsK.time = t0, t1


------------------------------------------------------------
8) 이 시나리오로 얻고 싶은 관찰(실험 체크리스트)
------------------------------------------------------------

- Phase2(대형 버스트)에서:
  - aborted 전송 증가, overhead 증가, delivery 급락이 나타나는지
- Phase3(TTL 짧은 메시지)에서:
  - 평균 지연/만료(drop/ttl)로 delivery가 크게 떨어지는지
- 에너지 고갈/activeTimes로:
  - 특정 시간대에 그래프가 바뀌면서 cost 오판이 늘어나는지(전이 지식 stale)
- 링크 간섭/거리 용량으로:
  - "만남 빈도"는 높은데 실질 전송량이 낮아지는 현상이 성능을 망치는지
